# Where your two email addresses go

This project has **two email addresses with two different jobs**, and they live in
two different places. Setting one never changes the other.

| | Private authentication address | Public contact address |
| --- | --- | --- |
| What it receives | Sign-in codes, password resets, password-change codes | Nothing — it is only displayed |
| Where it is stored | **Worker secrets / `.dev.vars`** (environment) | **D1**, edited in the dashboard under **Site content → Contact** |
| Who can see it | Nobody but the server (never rendered, never in an API response) | Every visitor, in the Contact page's `mailto:` link |
| Set it by | `OWNER_OTP_EMAIL` (and `OWNER_LOGIN_EMAIL`) | Dashboard form; no environment variable |
| Can it be changed by | The operator, in the server configuration | The owner, in the dashboard |

There is deliberately **no `PUBLIC_CONTACT_EMAIL` environment variable**: the
public address is editable site content stored in D1, and adding an environment
variable with the same meaning would create the second source of truth this
project avoids. Likewise there is **no `ADMIN_SESSION_SECRET`** to set — the
session-signing key is generated by the server on first use and stored in the
`app_secrets` table, so it never appears in a config file, a bundle or a chat
message.

## Exact locations at a glance

**Private administrator verification address** (login/OTP mail)

| | |
| --- | --- |
| Local file | `.dev.vars` in the project root (start from `.dev.vars.example`) |
| Variable | `OWNER_OTP_EMAIL` — where six-digit codes are delivered |
| Identity | `OWNER_LOGIN_EMAIL` — the address typed into `/admin` (may be the same) |
| Legacy fallback | `OWNER_AUTH_EMAIL` — honoured **only** when `OWNER_OTP_EMAIL` is unset |
| Production | Worker secret: **Sites → Secrets**, or `npx wrangler secret put OWNER_OTP_EMAIL` |
| Code that reads it | `worker/lib/owner.ts` → `configuredLoginEmail`, `configuredOtpEmail`, `seedOtpEmail`; enforced in `worker/lib/owner-security.ts` |

**Public contact address** (what visitors see)

| | |
| --- | --- |
| Where to set it | Dashboard → **Site content → Contact → Email**, then **Publish changes** |
| Stored in | D1 table `site_content`, document key `contact`, field `email` |
| Variable | None — this is content, not configuration |
| Code that reads it | `worker/lib/content.ts` (`CONTENT_KEY_CONTACT`, `DEFAULT_CONTACT`), served by `GET /api/content/contact`; displayed by `src/components/EmailCard.tsx` |

There are no variables named `ADMIN_VERIFICATION_EMAIL` or `PUBLIC_CONTACT_EMAIL`
in this codebase; those two concepts are the rows above. Adding them would create
a second, conflicting source of truth.

## 1. The private (authentication) address

### Variable names, exactly

| Variable | Required | Meaning |
| --- | --- | --- |
| `OWNER_LOGIN_EMAIL` | Yes | The administrator identity typed into `/admin`. Private. |
| `OWNER_OTP_EMAIL` | Recommended | Where the six-digit codes are delivered. Defaults to the login address when unset. |
| `OWNER_AUTH_EMAIL` | Legacy | Old name for the OTP destination. Still honoured **only** if `OWNER_OTP_EMAIL` is unset. Keep it during an upgrade, or drop it. |
| `OWNER_SETUP_TOKEN` | First run only | One-time value that allows the first password to be created. Delete it after setup. |
| `EMAIL_PROVIDER` | Optional | `local` (loopback catcher), `resend`, or `auto` (default). |
| `RESEND_API_KEY` | For real mail | The provider API key. |
| `EMAIL_FROM` | For real mail | A **verified** sender, e.g. `Arcade <verify@your-domain.example>`. |
| `EMAIL_REPLY_TO` | Optional | Reply-To shown on the verification mail. |

### Locally

1. `cp .dev.vars.example .dev.vars` (`.dev.vars` is git-ignored).
2. Set the values:

   ```dotenv
   APP_ORIGIN=http://127.0.0.1:8787
   OWNER_LOGIN_EMAIL=you@your-domain.example
   OWNER_OTP_EMAIL=private-inbox@your-domain.example
   OWNER_SETUP_TOKEN=replace-with-a-long-random-value
   EMAIL_PROVIDER=local
   ```

3. Restart the dev server (`npm run dev:full`). Wrangler reads `.dev.vars` at
   start-up; a running server will not pick up an edit.
4. With `EMAIL_PROVIDER=local` the code is **not** emailed — the development
   catcher returns it to the local sign-in response (and `npm run seed` prints
   it). That seam only exists on a loopback origin: on a deployed origin the
   local catcher is refused, so a production deployment can never "deliver" a
   code that was never sent.

### In production

Set the same names as Worker secrets — **Sites → Secrets**, or:

```bash
npx wrangler secret put OWNER_OTP_EMAIL
npx wrangler secret put RESEND_API_KEY
npx wrangler secret put EMAIL_FROM
```

`OWNER_LOGIN_EMAIL` and `OWNER_SETUP_TOKEN` are secrets too (the setup token only
until setup is complete). Then deploy the Worker so the new environment is
applied. `APP_ORIGIN` is injected by the platform; do not set it by hand.

### Verifying delivery without exposing the code

1. Open `/admin` and request a code. The response reports `sentTo` as a **masked**
   address (`p•••@your-domain.example`) plus `expiresAt` — never the code.
2. The security log records a `challenge.sent` event naming the purpose and the
   provider (`via resend`), never the code. See it under **Security** in the
   dashboard, or `GET /api/admin/security/state` while signed in.
3. In the Resend dashboard, **Emails → Logs** shows the message with status
   `delivered`, `bounced`, etc. That is the authoritative delivery record.
4. A failure comes back as `502 email_delivery_failed` with the provider's status
   in `detail` (e.g. `provider_error_403: ...`), and the challenge is stored as
   `failed` rather than silently pretending to have sent.
5. If the server has no key or sender at all, the API answers
   `503 email_unconfigured` and the dashboard says so instead of hanging.

Do not test by pasting a code anywhere public, and do not add a fixed code: none
exists, and the only thing that can unlock the dashboard is the code hashed
against the challenge the server just created.

## 2. The public contact address

* **Where:** dashboard → **Site content → Contact → Email**. It is saved to the
  `site_content` table (draft, then **Publish changes**), and this is the only
  place it is stored.
* **What it does:** the Contact page shows it, the "Open in email app" button is a
  `mailto:` link to it, and the floating mail button and mobile menu point at it.
  It is **never** used to send verification codes.
* **Locally and in production:** the same path — the dashboard. Local uses the D1
  emulation; production uses the deployed database, so publishing updates the
  live site without a rebuild or redeploy.

### Verify it

* Dashboard → Site content → Contact: the field shows the address you saved.
* `curl -s https://your-site/api/content/contact | jq .contact.email` returns it.
* The Contact page's email card links to `mailto:<that address>`.
* **Independence:** changing it does not touch the authentication address — the
  server refuses the request with `422 email_conflict` if you paste the private
  authentication address into that field. `npm run verify` covers both facts
  ("changing the contact address leaves the authentication address alone",
  "the private authentication address is refused as a public one",
  "the private address never appears in public content"), and
  `npm run audit:security` checks that no public response contains either private
  address or any secret name.

## 3. The email provider

The project ships with **Resend** support (`worker/lib/email.ts`) and a local
catcher for development. No other provider is wired in; adding one means
implementing the same `EmailProvider` interface.

1. Create a Resend account and an API key (`re_…`).
2. Verify the **sending domain** in Resend (DNS records: SPF, DKIM, and DMARC if
   you use it). Until the domain is verified, Resend only allows sending to your
   own account address — which is exactly the failure mode you would see while
   testing.
3. Set `RESEND_API_KEY` and `EMAIL_FROM` as secrets. `EMAIL_FROM` must be on the
   verified domain, e.g. `Arcade <verify@your-domain.example>`.
4. `EMAIL_PROVIDER=resend` forces the provider; leaving it unset (`auto`) uses
   Resend as soon as both the key and the sender exist.
5. Redeploy. The dashboard gate reports the provider state; **Security** shows
   whether delivery is configured.

### Diagnosing

| Symptom | Cause | Fix |
| --- | --- | --- |
| `503 email_unconfigured` | No key or no sender on the server | Set `RESEND_API_KEY` and `EMAIL_FROM`, redeploy |
| `502 email_delivery_failed` with `provider_error_403` | Key lacks permission, or sender domain not verified | Re-check the key and the domain in Resend |
| `502 … provider_unreachable` | The Worker could not reach Resend | Retry; check the provider's status page |
| Message "sent" but never arrives | Recipient spam filtering, or a sender on an unverified domain | Check Resend's log, then the inbox's spam folder |
| `409 auth_email_unset` | No OTP destination configured and none verified yet | Set `OWNER_OTP_EMAIL` |

## 4. Example file

The project's convention is **`.dev.vars.example` → `.dev.vars`** (Wrangler's own
format), not `.env`. An `.env.example` would be a second place to look for the
same secrets, so it is intentionally not shipped. Copy the block below into
`.dev.vars` and replace the placeholders — placeholders only, never real values,
in anything committed:

```dotenv
APP_ORIGIN=http://127.0.0.1:8787
OWNER_LOGIN_EMAIL=your-private-admin-email@example.com
OWNER_OTP_EMAIL=your-private-inbox@example.com
OWNER_SETUP_TOKEN=generate-a-long-random-value
EMAIL_PROVIDER=local
# RESEND_API_KEY=replace-with-your-provider-key
# EMAIL_FROM=verified-sender@example.com
# EMAIL_REPLY_TO=your-public-contact-email@example.com
```

For production, the same names go into **Sites → Secrets** or
`npx wrangler secret put <NAME>`, and the public contact address is set in the
dashboard — not here.
